Build your own UI5 control

A custom control is a JavaScript class that UI5 treats like any built-in control. You declare its API, describe how it renders, and add behaviour. In return you get binding, events, lifecycle and XML support for free.

Scene 01 / When do I need one?

Pick the lightest tool that does the job

Not every reusable piece of UI needs to be a control. A real custom control earns its place when you need an API: properties people bind to, events they listen to, and rendering you own.

New control

Nothing in the library fits, or you want to bundle several controls behind one API.

  • Control.extend(…)
  • You own metadata, renderer and behaviour
  • Can compose other controls inside
Scene 02 / Where it sits

Every control inherits a stack of features

When you call Control.extend, your class lands at the bottom of this chain. Each ancestor adds one capability, so you don't write any of it yourself.

sap.ui.base.Object
The root: extend() and class metadata
sap.ui.base.EventProvider
attachEvent, fireEvent, listener registry
sap.ui.base.ManagedObject
Properties, aggregations, associations, data binding, models
sap.ui.core.Element
Belongs to the UI tree: IDs, tooltips, custom data, browser event delegation
sap.ui.core.Control
Has a renderer and its own DOM: placeAt, invalidate, visible, busy state
demo.control.Rating
Only what's unique: stars, a value, a change event

Scene 08 / Two more patterns

  

    

      
Extend what exists, or compose from parts

      
Most real-world custom controls are one of these two. Extending keeps the parent's look and adds API. Composing hides several controls behind one clean API.

      
    
        
  • 1
    ExtensionReuse the parent renderer. Add metadata and handlers on top. Call the parent with Button.prototype.onAfterRendering.apply(this, arguments) when you override a hook it implements.
    • 
        
  • 2
    CompositeCreate children in init and store them in hidden aggregations, so they are destroyed with the parent and rendered with oRm.renderControl.

Scene 09 / Using it in an app

  
A namespace, a tag, and you're done

  
The XML namespace maps to the folder the control lives in. UI5 loads Rating.js on demand and treats it like any sap.m control: bindings, event handlers and all.

Scene 10 / Checklist

  
Rules to take back to your desk

  

    

      
Do

      
    
        
  • Use apiVersion: 2 renderersFaster, and UI5 patches the existing DOM instead of replacing it.
    • 
        
  • Pass the control to the root openStart("div", oControl)Writes the ID and data-sap-ui so events, focus and re-rendering work.
    • 
        
  • Change state only through generated settersThey validate types, update bindings and invalidate for you.
    • 
        
  • Return this from overridden settersKeeps method chaining working like every other control.
    • 
        
  • Use hidden aggregations for internal childrenThey're destroyed with your control, so nothing leaks.
    • 
        
  • Clean up in exitTimers, global listeners, and objects you created that aren't aggregated.
    • 
        
  • Prefix CSS classes and private members.demoRating, this._bTouched. Add ARIA roles in the renderer.
    • 
      

    

    

      
Don't

      
    
        
  • Use oRm.write() string renderingIt's deprecated and blocks DOM patching.
    • 
        
  • Change properties inside the rendererThe renderer reads state. Writing state during render triggers more renders.
    • 
        
  • Keep DOM references across rendersThe DOM may be replaced. Look it up with getDomRef() in onAfterRendering.
    • 
        
  • Suppress invalidation without updating the DOM yourselfYou get stale UI, as you saw in the live demo.
    • 
        
  • Write HTML for child controls by handCall oRm.renderControl(child) so the child keeps its own lifecycle.
    • 
        
  • Rely on global namesLoad dependencies through sap.ui.define and use the returned modules.
    •
